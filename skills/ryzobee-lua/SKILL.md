# RyzoBee Lua

依据目标固件的实际接口交付 Lua 源文件。**接口的维护位置是 [Ryzobee/ryzobee-firmware 的 docs](https://github.com/Ryzobee/ryzobee-firmware/tree/main/docs)，不是本技能。** 本包不保存模块白名单、函数签名、参数表、容量/字体常量或固定 Lua 模板。

## 先查文档，再写代码

1. 确认目标。用户指定固件版本、tag、commit 或本地工作树时使用它；未指定时读取官方默认分支当前文档，并说明该基线尚未与用户设备匹配。不要为了确认版本而擅自连接设备。
2. 读取 [固件文档导航](references/firmware-docs.md)，访问选定版本的文档索引/目录，再按任务阅读元数据、运行环境和涉及功能的正文。同一次任务尽量解析为一个 commit，文档、示例及必要源码都从这个版本读取。
3. 为实际使用的调用查清模块/入口、参数顺序与类型、字段/单位、返回值、失败语义、资源所有权和取消规则。只有找到这些依据后才使用该调用；文档缺项或互相冲突时，沿文档链接查同版本的公开实现/示例，并说明差异。不要用其它平台的同名 API 或旧对话补齐。
4. 根据查到的格式生成新脚本头部及文件名，填写真实作者信息和准确简介。维护旧脚本时先确认它的运行入口；示例用于理解接口，不代表用户实际接线、配置或权限。只读当前任务需要的资料，不为简单脚本遍历整个源码仓库。

网络不可用时可读取用户指定版本的本地文档或已提供的文档正文，并说明来源与版本。两者都没有时，一次性请求相关文档/目标版本；可以先梳理纯业务逻辑，但接口部分标为待核对，不猜方法，也不把“查不到”说成“固件不支持”。

## 编写原则

- 按功能拆成小函数，分开业务状态、渲染和输入处理；采用查证后的增量刷新和输入机制。
- 遵守所选版本的资源配额与生命周期。循环每轮工作、队列、日志和重试有界，保留取消检查和失败原因，按文档释放资源；不以吞掉错误换取表面成功。
- 分清受理、执行完成和结果未知；协议载荷按业务要求逐字节保留，不随界面文字风格改变。
- 将不可用、忙碌、损坏和未初始化等状态按对应接口契约处理，不把失败当作有效数据或首次运行而覆盖存档。
- 文档中的历史记录、测试 fixture 和 C 系统 UI 能力，不自动等于当前公开 Lua 能力或已完成实机验收。

## 验证与交付

从**同版本固件文档**查找可用的语法检查、示例与 Host/模拟器验证入口，阅读前置条件后做与任务相称的检查。技能不复制验证器或固定构建命令；有宿主验证工具时可使用它，但需确认目标版本与覆盖范围。缺少环境时明确标记未验证，不自动安装 SDK 或访问设备。

实际运行应覆盖主流程和相关失败/取消分支。语法通过不代表 native 调用正确；提前失败、未执行的回调、仅返回不可用或虚拟外设成功，都不能当作实机通过。截图/像素和物理设备结果单独说明。

使用 Link 模拟器时另查其运行时版本；最新固件文档不保证已进入 Link 的 Wasm。遇到版本差异应说明原因、选择匹配环境或与用户确认兼容方案，而不是用旧模拟器否定新固件接口。

交付包含脚本、所用文档的版本/链接、实际验证结果与剩余限制。验证是开发辅助，**不为 Link 发送设备新增仿真前置、审核或令牌**。

仅编写脚本不授权发送/运行设备、修改自启、配网、升级或擦除固件；这些操作须由用户明确请求。
